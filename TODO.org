** TODO Gizmo / Editable Data Environment (working name)

Build a hypermedia buffer service and client integrated with VRS. It should
function as a useful sticky-note service from the start, and provide a substrate
for lightweight interfaces that need a lasting surface beyond vrsjmp's command
bar: notes, documents, small forms and controls, and live widgets. Multiple
buffers can stay open and be revisited independently of a command-bar query.

Give saved buffers stable identities and ordinary VRS operations to create,
read, edit, list, and reopen them. Persist authored content and saved view
definitions independently of open windows and running view processes. Clients
manage presentation, including floating or pinned notes; the service makes the
same content accessible to scripts, editors, and other clients. vrsjmp can
create, find, and open buffers through those operations.

Support plain editable text, documents mixing text with live regions, and
standalone service-generated widgets through the same buffer surface. A widget
should not require surrounding prose. Reuse ordinary Lyric data, functions,
service calls, and entity actions for content and behavior. Start with a small
set of rendering and input capabilities; choose their representation through
concrete examples.

Keep authored text distinct from generated annotations and results. Refreshing
a live region must preserve edits, selection, and unrelated content. Services
remain authoritative for their data; a saved view can fetch current state when
reopened rather than depending on having received every update notification.
Decide how concurrent edits and view lifetimes work before adding more clients.

Recognizing shapes of data in ordinary text is one way to enrich a buffer:
associate them with entities, computations, reusable views, and available
actions. Also allow explicitly inserted views and buffers supplied by services.
Let structure and behavior be added gradually.

For example, write a travel outline with places and dates; recognize those
references, obtain data through VRS services, and attach useful views or actions
where they are needed. Investigate reusable view definitions matched to data
shapes, complementing entity-based action discovery. Naming remains open
(Gizmo / EDEN / CDEN); treat this as a larger project, separate from the first
iOS client.

First milestone: create and edit a plain sticky note, close it, restart the
service, and reopen it with its content intact. Then attach one live VRS view
with an action to that note, and open the same view as a standalone widget.
Verify that updates preserve the note's text and that its content and actions
are also accessible through ordinary VRS calls.

References: [[https://www.inkandswitch.com/embark/][Ink & Switch Embark]] and
[[https://www.inkandswitch.com/potluck/][Potluck]].

** TODO System-wide Job Configuration and Node Affinity

Goal: Manage processes and services more like =launchd=: declare the desired
configuration for the whole VRS system, then keep it running across available
nodes.

- Use one job model for long-running services, one-shot processes, and scheduled
  or periodic jobs (cron-like work).
- Treat service names as stable system-wide identities so callers do not need to
  know where a service is running.
- Allow jobs to have strict node affinity when they depend on that node's
  hardware, GUI session, credentials, or local data.
- Reconcile the configuration as nodes connect, disconnect, and restart: start
  missing jobs on permitted nodes and remove stale service registrations.
- Never move or fail over a strict-affinity job to another node.
- Keep placement and scheduling policy separate from the Lyric service
  implementation and calling semantics.

Examples: =:os_browser= is tied to an interactive Mac, while Feedbin and Oura
indexing are periodic jobs assigned to the always-on node. The conditional
startup currently written by hand in =scripts/init.ll= should eventually be
expressed through this model.

[[file:docs/manual.md::#how-vrs-runs][Core concepts]] covers =remote!=, =eval_remote=, and =vrsctl --node=
for sending code to a connected machine. Persistence, supervision, and automatic
placement remain follow-ups; remote evaluation does not install a durable job.

** TODO Durable Execution
Goal: Recovering from process or host failure

Use cases:
- Context captured inside functions: a function reads the active browser tab,
  then saves it. Retain that intermediate value across a failure or restart so
  recovery saves the original tab, even when the read is inside a wrapper or
  =begin= rather than an argument of the GUI's top-level call.
- Multi-step actions: save an article, then create a follow-up task. If the
  second step fails or the host restarts, retain the evaluated inputs and
  completed progress so recovery can resume that step without repeating the
  confirmed save. A =begin= or function body is a concrete place to explore
  this; retrying the whole function does not provide statement-level resumption.
- Recurring automation: a =loop= polls a feed, handles new entries, then sleeps.
  Recover its cursor, progress within the current iteration, and next wakeup
  after a crash or restart. Decide whether missed intervals are skipped or
  caught up, and how to avoid duplicate active loops or repeated completed work.

Distinguish confirmed effects from calls whose reply was lost: an unacknowledged
call may already have changed the external system. Define how recovery checks
or safely repeats those effects, rather than assuming they did not happen.

These use cases need durable progress and resumption. The smaller vrsjmp manual
retry design retains a failed call's arguments in memory and starts the whole
call again. =:on_click (save_page (active_tab))= snapshots the tab at interaction
time; =(save_active_tab)= cannot snapshot a read hidden inside its body. These
snapshots disappear when the vrsjmp service restarts. This is not resumption
inside a =begin=, function body, or loop.

** TODO Richer hypermedia documents and reusable views

Extend the current page/item/action protocol to lasting documents, multiple
open buffers, reusable views, forms, and richer input. Keep application behavior
in runtime programs and let clients choose their presentation.

Questions and intended properties:
- Compose views of data across applications, rather than tying a view to one app.
- Combine explicit actions with interactions inferred from entities or content.
- Let clients manage open views while service state remains available to programs.
- Use bidirectional requests and pubsub updates; decide what must be refetched
  after reconnecting instead of assuming every update was delivered.
- Keep the interface usable from automation and tests, including nested input.
- Decide which selection/navigation primitives are needed from concrete cases.
- Support terminal, graphical, and potentially voice presentations without
  requiring all clients to render identical widgets.

The obsolete v0.1 text_field/ul/li schema has been removed. No particular
document schema or update protocol is established by these notes.
Continue the concrete work under [[*Gizmo / Editable Data Environment (working name)][Gizmo / Editable Data Environment]]
and [[*Hypermedia format and React bindings for VRS state and pub/sub][Hypermedia format and React bindings]].

Related work: [[https://github.com/phoenixframework/phoenix_live_view][Phoenix LiveView]],
[[https://guide.elm-lang.org/architecture/][Elm]], and [[https://htmx.org][htmx]].

** TODO Shared persistence, relationships, and linked views

The entity/interactive system already associates operations and argument
providers with tagged values. It does not provide shared durable storage, an
automatic relationship graph, or proactive suggestions.

Explore what additional storage is useful without requiring all application
state to move into one object store:
- Persist entities and stable references where an application needs them.
- Link related data from separate services in one workflow.
- Recognize relationships from content or context, alongside explicit links.
- Generate reusable views of data independently of the client or application.
- Let actions operate on collections, in the spirit of embark-collect.
- Suggest useful links or operations without making those suggestions the
  only way to access the underlying data.

This retains the goals of the old Object Store proposal without treating its
central-store architecture as a prerequisite for the current entity system.
Connect with [[*Universal Entities, Search, Indexing][Universal Entities, Search, Indexing]],
[[*Sqlite IO for S-Expressions][SQLite I/O]], and [[*Personal Timeline service][Personal Timeline]].

Related work: [[https://github.com/oantolin/embark][Embark]],
[[https://mail.gnu.org/archive/html/hyperbole-users/2019-01/msg00037.html][Hyperbole]],
[[https://9p.io/sys/doc/plumb.html][Plumbing]], and entity-component patterns.

** TODO Runtime hosting and client-provided capabilities

Keep the client API small across local IPC, remote connections, and possible
in-process hosting for platforms that need it. The current daemon/client model
should not be mistaken for a completed mobile embedding setup.

Explore clients supplying local capabilities, input methods, or application
hooks back to the runtime. Relate this to [[*Revisit Runtime / Client Boundary][the runtime/client boundary]]
and [[*Controlling Terminal Mechanics for Connection][controlling-terminal mechanics]].
Decide ownership, nested requests, disconnect behavior, and capability routing.

** TODO Inspect why a process is waiting

Expose waiting reasons with useful metadata: a timer, a service reply, user
input, or an event. A client could inspect a waiting program and, where the
program permits it, supply the input it awaits.

Keep observation, cancelling work, and supplying a value distinct. Build on
the existing debugger and process model; do not imply that current dbg!
records provide resumable breakpoints or arbitrary interventions.
Connect with [[*Intercept and swap calls at runtime in vrs dbg][call interception]]
and the existing source-observation work.
