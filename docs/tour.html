VRS is a personal programming environment for building and composing software across your applications and devices. Its design combines a practical, exploratory style of programming with relentlessly uniform abstractions.

In VRS, services make their functions available to other programs and user interfaces. They are written in Lyric, VRS's scripting language. Like a Unix shell, it's built for hacking software together from command-line programs, local databases, and UI automation—whatever gets the job done.

The REPL, shell scripts, graphical applications, and even your editor are clients of VRS. Each can run code and use the full capabilities of the runtime.

That includes services on other devices. VRS connects devices as peers, so a program on a laptop can use a service on a home server through ordinary function calls.

Programs and user interfaces share the same exact representation. An expression from the REPL can be included directly as a user interface action. A recorded action is already a program, ready to edit and replay.

You build iteratively against the running system. The editor can call live functions, inspect their results, and insert those values into source code. Update a running service and the programs using it pick up the changes automatically.

A live, personal software ecosystem, grown one small script at a time—with every device a way into the whole system.

Working through the tour

With VRS running, the examples work in the vrsctl REPL. For live editing, use the editor. From the repository root:

SHELL
emacs -Q -L emacs -l vrs-mode scratch.ll

In the editor, C-c C-e evaluates an expression and C-c C-c evaluates the buffer.

Build a todo service

Evaluating this file starts a todo service. It keeps running after the REPL closes.

LYRIC
# todos.ll
(def todos '()) # In memory; resets when this file is reevaluated.

(defn! get_todos () todos)

(defn! add_todo (title notes)
  (def todo `(:title ,title :notes ,notes))
  (set todos (push todos todo))
  todo)

(defn! complete_todo (todo)
  (set todos (filter todos (fn (item) (not? (eq? item todo))))))

# Start or replace the service with these functions.
(spawn_srv! :todos :interface '(get_todos add_todo complete_todo))

The service is ready to use from the REPL:

LYRIC
(bind_srv :todos)
(get_todos)
# => ()

(add_todo "Buy coffee" "")
# => (:title "Buy coffee" :notes "")

(get_todos)
# => ((:title "Buy coffee" :notes ""))

VRS includes a browser service for Safari. Its active_tab function returns the current page's title and URL:

LYRIC
(bind_srv :os_browser) # With Safari open and the browser service running.
(active_tab)
# => (:title "VRS" :url "https://github.com/leoshimo/vrs")

The browser's result becomes the todo's notes:

LYRIC
(def tab (active_tab))
(add_todo "Try VRS"
  (format "{}\n{}" (get tab :title) (get tab :url)))
# => (:title "Try VRS" :notes "VRS\nhttps://github.com/leoshimo/vrs")

No Safari extension required.

Extend the service's interface with add_todo_from_tab:

LYRIC
# todos.ll — replace the final spawn_srv! with this block, then reevaluate.
(bind_srv :os_browser)

(defn! add_todo_from_tab (title)
  (def tab (active_tab))
  (add_todo title
    (if (and! (list? tab) (get tab :url))
      (format "{}\n{}" (or! (get tab :title) "") (get tab :url))
      ""))) # Leave notes empty when no tab is available.

(spawn_srv! :todos
  :interface '(get_todos add_todo complete_todo add_todo_from_tab))

The new action needs only the task title:

LYRIC
(bind_srv :todos) # Discover the newly added function.
(add_todo_from_tab "Try VRS")
# => (:title "Try VRS" :notes "VRS\nhttps://github.com/leoshimo/vrs")

A shell script uses the same call:

SHELL
vrsctl --bind todos -c '(add_todo_from_tab "Try VRS")'

The REPL experiment is now a service action that other programs can call.

Bring a result back into source

The editor can keep one of those todos as part of your program:

LYRIC
(def saved_todo
  (get (get_todos) -1))
# Put the cursor ON the closing parenthesis immediately after -1.
# C-u C-c C-e replaces that query with its result.

The source becomes:

LYRIC
(def saved_todo
  '(:title "Try VRS"
    :notes "VRS\nhttps://github.com/leoshimo/vrs"))

That todo is now part of the source. Edit it, keep it as an example, or pass it to another function; changes to the live list won't change it.

Build a user interface

The todo functions can become actions in a user interface. Describe each choice with a title and the expression to run when it is selected:

LYRIC
# todo-ui.ll
(bind_srv :todos)

(defn! todo_items (query)
  `((:title ,(format "Add todo: {}" query)
     :on_click (add_todo ,query ""))
    (:title ,(format "Add todo with this page: {}" query)
     :on_click (add_todo_from_tab ,query))))

For the query Buy coffee, both choices use that text as the task title; the second also saves the current page. Each :on_click is the actual call, arguments included. Selecting an item runs (eval (get item :on_click)).

The service supplies the page and evaluates selections:

LYRIC
# Append to todo-ui.ll, then evaluate the file.
(defn! root_page ()
  # The page names the function that supplies its entries.
  '(:push_page :title "Todos" :prompt "Add a todo…"
    :get_items todo_items :args ()))

(defn! get_items (callback args query)
  (apply (eval callback) (push args query)))

(defn! on_click (item)
  (eval (get item :on_click))
  :close) # Close the user interface after the selection.

# vrsjmp's clients read their pages from this named service.
(spawn_srv! :vrsjmp :interface '(root_page get_items on_click))

The page is self-describing: it includes what to display and what to run. A client only needs to request the choices and send back the selection. Here is a complete one-page client using fzf:

SHELL
#!/bin/sh
# todo-ui.sh — run with sh todo-ui.sh.
set -eu

# Evaluate VRS code with the user interface service's functions available.
vrs_eval() { vrsctl --bind vrsjmp "$@"; }

item=$(vrs_eval --raw -c '
  (begin
    (def page (root_page))
    (def query "Buy coffee")
    (def items (get_items (get page :get_items) (get page :args) query))
    (apply join (+ (list "\n") (map items display))))' | fzf)

vrs_eval -c "(on_click '$item)"

vrsjmp, VRS's graphical client, can display the same page:

LYRIC
(show_gui)

Typing Buy coffee in the GUI offers the same two actions as the shell script. Selecting either adds the todo. The shell displays whole entries; the GUI displays their titles. Neither client needs to know what a todo is: the shell script contains no todo function calls, and the GUI uses the same page and selection functions.

Show and complete todos

Add the live todo list to the page. Each todo becomes a choice whose action completes it, alongside the two actions for adding a new one:

LYRIC
# todo-ui.ll — replace todo_items and reevaluate the file.
(defn! todo_items (query)
  (+ `((:title ,(format "Add todo: {}" query)
        :on_click (add_todo ,query ""))
       (:title ,(format "Add todo with this page: {}" query)
        :on_click (add_todo_from_tab ,query)))
     (fuzzy_match query
       (map (get_todos) (fn (todo)
         `(:title ,(get todo :title)
           :subtitle ,(get todo :notes)
           :on_click (complete_todo ',todo)))))))

Search for coffee again: the GUI now offers to complete the todo created earlier. The GUI needed no rebuild or restart. Its new behavior comes from the service's response. The shell script offers the same actions on its next run; fzf filters that response locally, while the GUI sends each search to the service.

Record user interactions as code

A user interaction can become a program because its action is already an expression. VRS's built-in pub/sub lets one program publish a value for others to receive. Publish each selected expression on the :cmd topic:

LYRIC
# todo-ui.ll — replace on_click and reevaluate.
(defn! on_click (item)
  (def command (get item :on_click))
  (publish :cmd command) # Send the expression to subscribers before running it.
  (eval command)
  :close)

A second client can follow those calls as they happen:

SHELL
vrsctl --subscribe cmd --follow

Selecting an item now prints its call there. You can also invoke the selection handler from the REPL:

LYRIC
(bind_srv :vrsjmp)
(on_click '(:on_click (add_todo "Buy coffee" "")))

The follower prints: 

(add_todo "Buy coffee" "")

The recording is already a program. Changing coffee to tea changes what it does:

LYRIC
(bind_srv :todos)
(add_todo "Buy tea" "")

The recording calls the todo service directly; the user interface needn't be open. The command-macro service collects these expressions into a sequence to replay together.

Build a process manager from ps

Turn shell output into values with discoverable actions. A process can offer Copy PID or Terminate process in the editor, terminal, and GUI, with the actions defined once. Start with the process list:

LYRIC
# processes.ll
(defn! get_processes ()
  (def output (exec "sh" "-c" """
    ps -axo pid=,comm= |
      awk '{ pid=$1; sub(/^[[:space:]]*[0-9]+[[:space:]]+/, ""); print pid "\t" $0 }'
    """))
  # (get output :stdout) => "1\t/sbin/launchd\n..."
  (def rows (decode :tsv (get output :stdout) :columns '(:id :title)))
  # (get rows 0) => (:id "1" :title "/sbin/launchd")
  (map rows (fn (fields) `(:os/process ,@fields)))) # Tag each row as a process.

(get (get_processes) 0)
# => (:os/process :id "1" :title "/sbin/launchd")

The shell output, decoded rows, and tagged processes are all visible as you build the function. The editor evaluates the intermediate expressions against the running system.

The tag makes each process an entity: a value the runtime can match to applicable actions.

Give each process its actions

Two ordinary functions declare which values they apply to through interactive metadata:

LYRIC
# Add to processes.ll.
(defn! copy_pid (process)
  "Copy PID"
  (interactive :os/process) # Offer this action for values tagged :os/process.
  (exec "pbcopy" :stdin (get process :id)))

(defn! terminate_process (process)
  "Terminate process"
  (interactive :os/process)
  (exec "/bin/kill" "-TERM" (get process :id)))

The runtime can now find the actions for a process value:

LYRIC
(def process (get (get_processes) 0))
(entity_functions process)
# => (copy_pid terminate_process) # Discovered from their interactive metadata.

(copy_pid process) # The actions remain ordinary functions.

In the editor, C-c C-v on (get_processes) can insert a chosen process into source, and C-c C-a offers its actions. Choosing Copy PID produces:

LYRIC
(copy_pid '(:os/process :id "413" :title "/usr/bin/sleep"))

The action menu wrote the call into your source. You can change its argument before running it with C-c C-e.

Offer processes as function arguments

Choosing Copy PID can prompt for a process, too. Register get_processes as the provider of argument choices, then export the functions:

LYRIC
# Append to processes.ll, then evaluate the file.
(set_entity_completions :os/process 'get_processes)
(spawn_srv! :processes
  :interface '(get_processes copy_pid terminate_process))

Another client learns the actions when it binds the service:

LYRIC
(bind_srv :processes)
(entity_functions (get (get_processes) 0))
# => (copy_pid terminate_process)

The full vrsjmp service already knows how to browse functions and request their arguments:

SHELL
# Add (bind_srv :processes) to scripts/vrsjmp.ll before running.
# With the usual VRS services running; replaces the small todo user interface.
vrsctl scripts/vrsjmp.ll
./scripts/vrsjmp_cli.sh

In Browse Functions, choosing Copy PID offers the live process list for its argument. In the GUI, Cmd-K on a process offers the other direction: pick a process, then an action. The editor uses the same declarations for its action menu and function browser.

Three user interfaces, one set of actions.

Connect more of your software

The ps wrapper turns a command's output into functions and values the rest of VRS can use. Existing services take the same approach with other ways into applications and hardware:

  • Safari uses AppleScript for the active page and SQLite for tabs synced from other devices. Both are available through the browser service.
  • Apple Notes reads titles from SQLite, opens notes through application URLs, and creates them with AppleScript.
  • Antinote reads its SQLite database and opens notes through URLs. Its tagged notes also work with the action and argument menus above.
  • Feedbin runs feedbinctl to search articles and save pages.
  • Keyboard brightness reaches a private macOS framework through osascript to read and change the backlight.
  • Ditoo calls a dedicated CLI to drive a Bluetooth pixel display.

Make a unicorn leap when a todo is completed

Make completing a todo trigger a desktop animation. The todo service publishes an event; a separate program supplies the celebration:

LYRIC
# todos.ll — replace complete_todo and reevaluate the file.
(defn! complete_todo (todo)
  (if (contains? todos todo)
    (begin
      (set todos (filter todos (fn (item) (not? (eq? item todo)))))
      (publish :todo_completed todo))))

A separate service responds by running unicornleap, which animates a unicorn across the desktop:

LYRIC
(defn! celebrate (todo)
  (exec "unicornleap"))

(def celebration
  (spawn_srv! :celebration
    :interface '()
    :topics '((:todo_completed celebrate)))) # Call celebrate with each event's value.

Complete a todo:

LYRIC
(bind_srv :todos)
(def todo (add_todo "Finish this example" ""))
(complete_todo todo)
# A unicorn leaps.

The todo service publishes what happened; the subscriber decides what to do with it. Stop the animation service while leaving the todo list running:

LYRIC
(kill celebration)

Another listener could redraw an e-ink agenda. These events are local to one VRS node; their handlers can call services on other devices.

Keep an index fresh

Keep a search index up to date with a program that works, sleeps, and repeats. The job and the wait are ordinary sequential code:

LYRIC
(def indexer
  (spawn (fn ()
    (loop
      (exec "feedbinctl" "index") # With feedbinctl configured.
      (sleep 900))))) # Wait fifteen minutes after each run finishes.

The REPL stays free. The program survives the client disconnecting, and sleeping occupies no operating-system thread. Stop it explicitly, or it ends with the runtime:

LYRIC
(kill indexer)

The Feedbin service uses this pattern with error reporting and a name so reloading replaces its previous indexer.

Run the todo service on a home server

The todo service can run on a home server and still capture the page open on the laptop. With mac-mini connected as a VRS peer, send it the same todos.ll:

SHELL
# Stop the laptop's example service; its in-memory todos are discarded.
vrsctl -c '(kill (find_srv :todos))'
# Read the file locally and start it on mac-mini with an empty list.
vrsctl --node mac-mini ./todos.ll

The laptop discovers the remote service and calls it in the usual way:

LYRIC
(bind_srv :todos)
(add_todo_from_tab "Try VRS")
(get_todos)
# => ((:title "Try VRS" :notes "VRS\nhttps://github.com/leoshimo/vrs"))

The todo service runs on the server and asks the laptop's :os_browser service for the page. Neither function call needs a hostname. The user interface from earlier works with the remote list, too.

Edit todos.ll on the laptop and send it again to replace the running service. The editor can do this through an expression:

LYRIC
(eval_remote "mac-mini" (read_script "./todos.ll"))

Existing bindings pick up the new service. The source stays on the laptop; the program runs on the server.

Use hardware attached to another device

The same function-call interface reaches hardware. With the Ditoo service and its Bluetooth display set up on the home Mac, a program on the laptop can write to it:

LYRIC
(call_timeout 120) # Allow time for the Bluetooth connection and upload.
(bind_srv :ditoo)
(ditoo_text "OFF DUTY")

Only the hosting Mac needs Bluetooth access. An editor command or build script on another device can use the display through the same function.

Keep a debugger in your source

Inspect live calls, arguments, and results from an expression in source. dbg! records the execution while returning the expression's usual value. Open a viewer for the trace:

SHELL
vrsctl dbg --web
# Or use vrsctl dbg for the terminal viewer.

The dbg! expression returns process names while recording how they were computed:

LYRIC
(bind_srv :processes)
(dbg! (map (get_processes) (fn (process) (get process :title))))

The viewer shows calls, arguments, results, and source locations. Expanding map reveals the individual calls. The query stays in source, ready to rerun.

This records the service call and the local mapping. To inspect code inside the service, put dbg! there too.

The debugger is another client of the runtime. Its history is ordinary program data:

LYRIC
(get (dbg_history) :records) # The same recording the viewers read.

History is bounded and kept in runtime memory. The debugging guide covers filters, source history, and cancellation.
